# Windows: установка, приемка и лицензии, этап 06

Статус на 14 октября 2026: локальная среда — macOS ARM64. Реальных Windows runner, сертификата подписи и проверенного update feed у проекта сейчас нет. Таблица ниже фиксирует отсутствие испытаний, а не успешную поддержку продукта.

| Цель | Установка и удаление на этой ОС | Настоящий процесс нужной архитектуры | Пользовательские сценарии и устройства |
|---|---|---|---|
| Windows 10 22H2 x64, build 19045 | NOT_RUN | NOT_RUN | NOT_RUN |
| Windows 11 x64, build 22000+ | NOT_RUN | NOT_RUN | NOT_RUN |
| Windows 11 ARM64, native ARM64 | NOT_RUN | NOT_RUN | NOT_RUN |

Windows Server на обычном GitHub hosted runner не считается Windows 11. Работа x64-приложения под эмуляцией на ARM64 не считается native ARM64. Windows 10 ARM64 и 32-bit Windows в матрицу MeetSpace не входят.

## Основания и границы совместимости

Проверенный upstream — Electron 44.7.1: [README именно этой версии](https://raw.githubusercontent.com/electron/electron/v44.7.1/README.md) указывает Windows 10 и новее и бинарники x64/ARM64. [Объявление Electron 44](https://www.electronjs.org/blog/electron-44-0) описывает прекращение ia32. Это основание для выбора сборки; оно не заменяет запуск MeetSpace на каждой целевой ОС.

[Документация Electron ARM](https://www.electronjs.org/docs/latest/tutorial/windows-arm) отдельно требует совместимых native-зависимостей и локального расположения приложения для Chromium sandbox. Runtime-зависимость MeetSpace `ws` написана на JavaScript; optional native accelerators в текущий payload не включены. Упаковщик проверяет PE machine у самого приложения и каждой DLL, а Windows-приемка дополнительно сверяет `IsWow64Process2` у реально запущенного процесса. Поле модели компьютера помогает описать VM, но не доказывает наличие физического ARM-компьютера: тип хоста/гипервизора записывает оператор.

## Безопасная автоматическая приемка

Файл: `desktop/scripts/windows-acceptance.ps1`. Запускать только в новом одноразовом Windows client account/VM, без MeetSpace, сохраненных аккаунтов и личных данных. Скачанные EXE и соседний EXE.json должны происходить из проверенного CI artifact того же исходного коммита; JSON не является самостоятельной цифровой подписью установщика.

Примеры из корня checkout, для каждой машины отдельно:

```powershell
pwsh -NoProfile -File desktop/scripts/windows-acceptance.ps1 `
  -Installer C:\Acceptance\MeetSpace-0.6.0-win-x64-test-setup.exe `
  -ExpectedArchitecture x64 -ExpectedOS win10-22h2 `
  -EvidenceDirectory C:\Acceptance\evidence-win10 -DisposableAccount

pwsh -NoProfile -File desktop/scripts/windows-acceptance.ps1 `
  -Installer C:\Acceptance\MeetSpace-0.6.0-win-x64-test-setup.exe `
  -ExpectedArchitecture x64 -ExpectedOS win11 `
  -EvidenceDirectory C:\Acceptance\evidence-win11-x64 -DisposableAccount

pwsh -NoProfile -File desktop/scripts/windows-acceptance.ps1 `
  -Installer C:\Acceptance\MeetSpace-0.6.0-win-arm64-test-setup.exe `
  -ExpectedArchitecture arm64 -ExpectedOS win11 `
  -EvidenceDirectory C:\Acceptance\evidence-win11-arm64 -DisposableAccount
```

Скрипт отказывается работать при существующих MeetSpace-процессах, профилях, uninstall-записях, протоколе, автозапуске или ярлыках. Он проверяет SHA-256 установщика, версию, исходный коммит и fingerprint дерева, реальную client ОС (`ProductType=1`) и архитектуру, затем устанавливает приложение per-user в новый локальный каталог со случайным именем. Хэши установленного EXE, app.asar и каждой DLL должны совпасть с проверенным manifest. Флаги NSIS `/D` и `_?=` расположены последними, согласно [официальной документации NSIS](https://nsis.sourceforge.io/Docs/Chapter3.html).

В **unsigned test** сборке включается один фиксированный diagnostic switch с 43-символьным случайным nonce. `desktop/src/acceptance.ts` принимает его только для packaged win32, immutable `releaseMode=test`, отключенного release trust и валидного исходного коммита. Каталог профиля и результата выводится из `%TEMP%\MeetSpaceAcceptance\<nonce>`; произвольных URL, скрипта, выходного пути, удаленной отладки или отключения TLS/sandbox нет. Проверяются реальные renderer/preload: context isolation, sandbox, отсутствие Node в странице, минимальный bridge v5, CSP, запрет локального API через renderer, пустой список серверов и выключенный автозапуск. Сервер не выбирается, логин и backend-запросы не создаются.

Второй процесс запускается с тем же nonce и фиксированным безопасным `meetspace://open/meetings/.../join`. Первый процесс должен получить маршрут, сохранить одно окно и завершиться после записи результата. Удаление запускается только через uninstaller внутри созданного каталога. Проверяются удаление EXE, регистрации, ярлыков и протокола. В конце могут удаляться только два каталога с созданным nonce; обычные пользовательские профили не удаляются. При сбое установка/остатки сохраняются для разбора внутри disposable VM. Ее уничтожают после сохранения evidence.

Автоматическое `checks.protocol` означает проверку registry command и передачи CLI deep link существующему экземпляру. Полный запуск протокола через Windows ShellExecute вынесен в ручной сценарий: автоматически добавлять тестовый nonce в глобальную регистрацию протокола было бы неверной проверкой реального поведения.

Файлы результата: `windows-acceptance-<target>.json`, его SHA-256 и для test-сборки `runtime-<target>.json`. Evidence содержит версию, installer digest, sourceCommit/sourceTreeSha256, actual OS build/ProductType, native/process architecture, отдельные проверки и время. `testBuild:true` никогда не удовлетворяет signed-release gate. Учетных данных, токенов, SDP или содержимого пользовательских сообщений в отчете нет.

## Подписанный кандидат и ручная приемка

Release packaging исключает `dist/acceptance.js`; обычное приложение игнорирует diagnostic switch. Для будущего подписанного кандидата тот же PowerShell helper проверяет действительную Authenticode-подпись, устанавливает и запускает обычный EXE без тестового флага в чистом disposable account, собирает native OS/process evidence и удаляет установку. Он **не ставит PASS renderer/CSP и product UI**: результат остается NOT_RUN, завершение — ненулевое. Нужна отдельно записанная приемка точного подписанного installer digest, а не перенос результатов test-сборки или ручная замена false на true в автоматическом отчете.

Оператор будущего release-кандидата прикладывает датированный протокол с собственным именем, build/hash, ОС, типом машины/гипервизора и наблюдениями:

1. Установка обычным пользователем, ожидаемые названия/иконки и publisher, выбранный локальный путь; ярлыки Desktop/Start Menu запускают именно установленную версию. Предупреждения SmartScreen фиксируются отдельно; подпись сама по себе не гарантирует репутацию.
2. Запуск из ярлыка, повторный запуск, перезапуск Windows; один экземпляр приложения. При первом запуске автозапуск выключен. Пользователь включает его в настройках, проверяет запуск после входа Windows, затем выключает и проверяет отсутствие запуска. Ничего не включается автоматически во время установки.
3. Нажатие настоящей `meetspace://` ссылки через ОС при закрытом и открытом приложении; переход в ожидаемую встречу после подключения/авторизации, отсутствие второго экземпляра. Неверный host/path, посторонний HTTPS URL, query с токеном и произвольная команда отклоняются. Сервер без явного выбора не меняется.
4. Light/dark, масштаб/DPI и несколько мониторов, свернуть/закрыть в tray/восстановить/полный выход; уведомления ОС, настройки звука, восстановление окна после смены монитора. Screenshot не должен содержать реальные пароли или сообщения.
5. Вход на разрешенный тестовый сервер, прямой/групповой чат, папки, календарь/история, запись и вложение с отменой Save dialog; смена сервера/выход очищают прежнюю идентичность. Проверить offline, просроченную сессию, отказ TLS и недоступную capability без создания фиктивных данных продукта.
6. Две реальные стороны WebRTC: камера/микрофон, выбор/смена устройства, screen/window picker, разрешения и отказ ОС, TURN при недоступном прямом пути. На ARM64 — native процесс; отдельно фиксируются выбранные устройства и драйверы. Синтетические локальные media-тесты этого не заменяют.
7. Запланированное подписанное обновление проверяется только после появления реального доверенного feed, ключей и подписанных старой/новой версий: download, отказ подписи/хэша/rollback, отмена, установка и восстановление. При текущем отсутствии feed этот пункт NOT_RUN.
8. Удаление установленного кандидата: приложение, собственные ярлыки/протокол/опциональный автозапуск удалены; политика сохранения пользовательских данных проверена и записана. Для release-кандидата чистый disposable профиль после теста уничтожается вместе с VM, а не скриптом из реальной рабочей учетной записи.

Ручной протокол должен иметь собственный digest и ссылку из итогового отчета; доверенный release gate проверяет его связь с тем же installer/source tree. Один только hand-edited JSON не является доказательством. До такой приемки всех трех ОС заявлять полностью подтвержденную Windows-поддержку нельзя.

## Лицензии, название и ресурсы

`desktop/package.json` объявляет приложение `UNLICENSED`; собственной лицензии проекта в исходном репозитории не найдено. Лицензии зависимостей не выдают права на публикацию самого MeetSpace и предоставленного брендинга. В unsigned test installer сохранено явное название MeetSpace Test. Иконка взята из существующего `frontend/public/branding/meetspace-app-blue.svg`; `desktop/resources/icon-source.json` хранит SHA-256 оригинала и преобразование в PNG/ICO, а не новую лицензию на изображение.

`desktop/scripts/generate-third-party-notices.mjs` берет фактический установленный closure production-зависимостей и их peers из обеих locked npm-установок, добавляет лицензию Vite для внедренного runtime helper и сохраняет полные найденные LICENSE/COPYING/NOTICE. Неизвестная отсутствующая зависимость или отсутствие текста лицензии останавливает генерацию. Несколько license-файлов и составные лицензии не обрезаются. Инвентарь консервативен: присутствующие type-only peers могут оказаться перечислены, даже если не входят в renderer.

Выходные ресурсы: `THIRD_PARTY_NOTICES.txt` и `third-party-licenses.json`, с версиями, SHA-256 текстов и обоих lockfiles. Сейчас перечислены 14 компонентов: MIT-библиотеки React/Router/query/ws и др., OFL Inter, ISC/MIT lucide, а также полные дополнительные notices Vite. Отдельные `LICENSE.electron.txt` и `LICENSES.chromium.html` должны сохраняться в установленном payload Electron. Шрифты и иконки поэтому не остаются без сопровождающих условий. Генерация детерминирована при тех же установленных пакетах; новые зависимости требуют нового inventory и проверки.

Текущие локальные проверки: пять Node-тестов acceptance gates/nonce и лицензий прошли; `desktop/tests/windows-acceptance-structure.ps1` прошел на официальном portable PowerShell 7.6.7 для macOS ARM64 (архив сверялся с published SHA-256). Он проверяет синтаксис реального helper, запись UTF-8 JSON без BOM, чтение PE machine x64/ARM64 и отклонение поврежденных DOS/PE-заголовков/offset. Команда для повторения: `pwsh -NoProfile -File desktop/tests/windows-acceptance-structure.ps1`.

Эти проверки **не равны** выполнению NSIS/Win32/реального UI на Windows. PowerShell 5.1 runtime также отдельно не запускался. Отчет Stage06 отдельно перечисляет фактические результаты и оставшиеся NOT_RUN.

Профиль повторения: сначала 10 циклов warmup, затем 100 join/leave и отдельно 100 открытий/закрытий чата. До нагрузки, после нагрузки и после logout/полного выхода сохраняются main/renderer heap snapshots после GC (если разрешено диагностической сборкой), Electron process metrics, счетчики процессов и Windows handles/CPU из Process Explorer/Performance Monitor. Отдельно учитываются live MediaStreamTrack/PeerConnection, WS/SSE, capture callbacks, активные Range/Save requests, таймеры и подписки. Debug-инструменты не включаются произвольным флагом в production release; измерение диагностической сборки и приемка signed кандидата имеют разные artifact hashes и явно разный scope.

Для воспроизведения отказов нужны управляемая тестовая сеть/тестовый сервер и согласованные тестовые аккаунты. Оператор фиксирует порядок действий, warmup, длительность idle-окна, модель устройства/драйверы, способ GC/сбора метрик и метод искусственного crash/suspend; реальные секреты и SDP в evidence не попадают. После crash/sleep/wake повторяется вход в разговор, а после полного выхода проверяется отсутствие принадлежащих приложению процессов и захвата устройств.

Локальный аудит нативных сервисов и подтвержденное исправление очистки описаны отдельно в `07_NATIVE_LIFECYCLE.md`. До заполнения этой матрицы результатами реальных устройств/VM остаются blockers для заявления о полной Windows-поддержке; отсутствие ARM64 runtime-проверки прямо блокирует заявление о подтвержденном native ARM64 опыте.

### Возможная приемка в UTM

Windows 11 ARM64 в UTM на Apple Silicon подходит как **Windows 11 ARM64 VM** для проверки установленного native ARM64 приложения: установка/UI/сеть/tray/deep links/удаление. На момент финального native-service профиля VM находится на первоначальном экране подготовки Windows; запуск MeetSpace в ней пока не подтвержден, поэтому результаты **NOT_RUN**. UTM виртуализирует ARM64 на Apple Silicon; x64 на таком Mac требует эмуляции, поэтому ее результаты учитываются отдельно и не подменяют native ARM64 или аппаратные x64 испытания. [Официальное описание UTM](https://mac.getutm.app/).

Полный GPU/WebRTC/device опыт и аппаратная производительность остаются отдельными проверками: у UTM для Windows нет аппаратного 3D-ускорения. [Ограничение GPU](https://mac.getutm.app/). USB sharing поддерживается QEMU backend, встроенную Apple webcam нельзя передать таким способом, а совместимость внешних USB устройств зависит от устройства и драйвера. [Ограничения USB](https://docs.getutm.app/guest-support/sharing/usb/). Системный sleep/wake гостя и хоста записывается раздельно; VM не доказывает работу камеры/драйвера/GPU или энергосбережения на физическом Windows ARM64 устройстве.
