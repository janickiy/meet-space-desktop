# Установщик сервера по SSH: протокол Android и Desktop

Windows и Linux используют тот же подписанный установщик сервера, что и
[MeetSpace Android](https://github.com/janickiy/meet-space-android/tree/9789b64ecc28fe265d4a059d36912db39ab0c2eb/installer).
Это установка серверной части MeetSpace на подготовленную Ubuntu через SSH.
Установщик Windows-приложения NSIS остаётся отдельным артефактом.

## Интерфейс и локальное хранилище, 24 октября 2026 года

Мастер Windows/Linux использует композицию предоставленного макета: пять
шагов подключения, отдельные состояния проверки и компактный итоговый экран.
После подтверждённого `completed` показаны готовый адрес и действие подключения;
десять завершённых серверных этапов и 100% доступны в раскрываемом блоке.

Недоступность системного хранилища паролей на компьютере не отменяет успешную
установку сервера. Интерфейс сообщает об этом отдельно и предлагает
«Проверить хранилище» после его разблокировки. Повторный `servers:list` пробует
загрузить и расшифровать существующий vault, не перезапуская установку.
Повреждённый vault не перезаписывается. После сбоя сохранения используется
актуальное состояние памяти, чтобы не возвращать cookies уже завершённой сессии.
Незашифрованного резервного режима нет.

Проверены 66 целевых тестов broker/security/platform и настоящий Electron
с детерминированным SSH-транспортом: 13 сценариев, 23 снимка, обе темы,
узкое окно и текст 150%. Сценарий завершения с заблокированным хранилищем
сохраняет 100%, а после успешной повторной проверки разрешает подключение
без повторного `apply`. Это не повторная установка сервера и не полная
приёмка на каждой целевой ОС.

## Граница доверия

`desktop/src/ssh/protocol.ts` проверяет RSA/SHA-256 подпись исходных байтов
`release.json`, SHA-256 `runner.py` и `docker.asc`, версию и production-профиль.
Дополнительно SHA-256 публичного ключа издателя закреплён в исходном коде
Windows. Подмена всего комплекта на другую корректно подписанную пару ключей
отклоняется. Изменение доверенного ключа требует явного обновления приложения.

Передача по SSH использует фиксированную команду запуска Python с правами root
либо через `sudo -n`, без PTY, agent forwarding и интерактивного sudo. Публичный
комплект, разрешённое действие и JSON-запрос передаются на stdin как данные в
base64. Поля пользователя не интерполируются в shell/Python. Сам runner повторно
проверяет подпись и контрольные суммы перед выполнением действия.

Разрешены только `plan`, `apply`, `status`, `cancel`, `resume`. Максимальный
bootstrap — 512 КиБ, ответ MSI1 — 256 КиБ. Парсер отклоняет повторяющиеся JSON
ключи, некорректный UTF-8, небезопасные числовые значения, чрезмерную вложенность,
неизвестные состояния, небезопасные имена фаз и коды ошибок. Сообщения
подпроцессов, пароли и серверные секреты не являются частью протокола.

## План и повторное подключение

Текущий подписанный комплект закрепляет backend commit
`a7d037ea9c228590bcd482d5eba410318029c4dd` репозитория
`janickiy/meet-space`, контрольную сумму архива и исходных файлов. Этот снимок
включает совместимые настройки SMTP и оптимизации сборки. Новая установка
скачивает именно его; появление другого GitHub Release не меняет выбранный код.
Обновление снимка требует проверки и новой подписи комплекта.

Для совместимости поддерживаются подписанные рецепты с политикой
`github-latest-stable-v1`: они выбирают последний стабильный GitHub Release,
разрешая default branch только при HTTP 404. Их `sourceLock` фиксирует
репозиторий, канал, ref, версию, полный commit, время commit,
неизменяемый URL архива, SHA-256 архива и требуемых исходных файлов. Windows
восстанавливает эффективный манифест, проверяет SHA-256 подписанного рецепта и
эффективного release, затем SHA-256 всего плана. Отдельно проверяются
Ubuntu/архитектура и версии пакетов Docker из подписанного рецепта, каталог
`/opt/meetspace`, проект `meetspace`, действия установки и параметры пользователя.

План действует 15 минут; допустимое опережение часов сервера — 30 секунд.
Истёкший план отклоняется перед новой установкой. Явный режим чтения сохранённого
плана допускает восстановление существующего задания; срок не подменяет проверку
подписи, хешей и связи задания с планом. План текущего закреплённого рецепта
не содержит `sourceLock`; попытка подменить им подписанный снимок отклоняется.

Публичный ticket связывает SSH host/port/user, принятый SHA-256 fingerprint,
UUID v4 задания и hash подтверждённого плана. Для существующего управляемого
задания используются его исходные `existingJobId` и `existingPlanHash`.
Ответ состояния должен совпасть по jobId, planHash, commit, domain и версии.
Фазы должны идти в ожидаемом порядке; `completed` допускается только после
всех десяти фаз. События ограничены 64 элементами и возрастающей нумерацией.

Подпись рецепта удостоверяет исполняемый установщик, правила выбора и
инфраструктуру. Она не является подписью самого upstream GitHub Release.

### Совместимость сохранённых заданий после исправления времени

Исходный подписанный комплект с release SHA-256 `f385643e…` сохранён побайтно
в `desktop/resources/server-installer/legacy/f385643e8019e89cf38bea29c15477cde6baddbe74bcab0f94a18d696e5b637a/`.
Он используется для восстановления ticket, чей план связан именно с этим
комплектом. Если локальная карточка отсутствует, после `PLAN_CHANGED` или
`EXISTING_INSTALLATION` от текущего комплекта допускается единственный дополнительный запрос чтения
плана прежним комплектом. Принимается только подтверждённое существующее
задание с обоими `existingJobId` и `existingPlanHash`; новая установка прежним
комплектом запрещена. Подпись, исходный доверенный ключ, полный hash плана
и привязка к хосту проверяются обычным способом. Новые планы используют
исправленный комплект. Произвольный путь или манифест из ticket не исполняется.

Ошибка `IMAGE_BUILD_FAILED` от 23 октября возникла в сборке frontend:
`VITE_BUILD_TIME must be a UTC timestamp`. Серверный frontend принимает
метку времени в формате `YYYY-MM-DDTHH:mm:ssZ`, а прежний подписанный манифест
содержал смещение `+03:00`. Исправление сохраняет тот же момент времени и не
изменяет backend commit. Для уже созданного задания одного обновления Desktop
недостаточно: оно намеренно продолжает пользоваться исходным подтверждённым
планом. На тестовом хосте выполнена отдельная проверяемая пересборка frontend
с нормализованной меткой, сохранены сведения о ремонте и checkpoint проверенного
образа; затем вызван штатный `resume`. Подписанный комплект на сервере, исходники
и hash плана при этом не менялись. Вывод сборки доступен администратору через
`docker buildx history logs`; сырые логи не передаются в renderer.

## SMTP и ускорение установки

Мастер предлагает SMTP-сервер, порт, адрес отправителя, логин и режим TLS
(STARTTLS или TLS). Настройку можно пропустить; в этом случае email-доставка
не включается. Пароль запрашивается только при подтверждении плана и передаётся
отдельным полем `smtpPassword` в `apply`. Он не входит в публичный план,
журнал состояния или локальную карточку восстановления. На сервере параметры
сохраняются атомарно в `config/smtp.env` с правами `0600`; `resume` использует
этот файл и отклоняет отсутствующий либо изменённый секрет.

SMTP по умолчанию выключен. Если настройка пропущена, после завершения установки
можно создать `/opt/meetspace/config/smtp.env`, подключить его только к `api` и
`product-worker`, установить для них `EMAIL_PROVIDER_MODE=smtp`, проверить
Compose и пересоздать только эти два сервиса. Точные команды, права доступа и
правила экранирования приведены в разделе
[Enable email later after skipping SMTP](https://github.com/janickiy/meet-space-android/blob/9789b64ecc28fe265d4a059d36912db39ab0c2eb/installer/README.md#enable-email-later-after-skipping-smtp).
До подключения SMTP приглашения и напоминания по email не отправляются.

Backend отправляет приглашение сразу и одно напоминание за три часа до
запланированной встречи. Фактическая доставка требует рабочего SMTP-аккаунта
и настроенного почтового домена; успешная сборка приложения не доказывает
попадание письма во входящие.

BuildKit сохраняет кэш модулей и компилятора Go, а также загрузок npm.
Добавляемые кэши разделены по архитектуре и закреплённой версии toolchain;
существующие кэши исходных Dockerfile не дублируются. При продолжении runner
проверяет ID, архитектуру и метки уже готовых образов и не собирает их повторно.
Замеры этапов сохраняются в `jobs/<UUID>/image-timings.json`. Первая установка
на чистом сервере по-прежнему требует загрузки зависимостей и компиляции.
Компактный профиль ограничивает параллелизм и память процессов Go/Node,
сохраняя все компоненты приложения. Глобальная очистка Docker не выполняется.

## Поддержка хоста и эксплуатационные ограничения

Сохранены ограничения Android runner: Ubuntu 22.04/24.04 с systemd, Python 3,
OpenSSL, root либо sudo без пароля, amd64/arm64. Минимальный компактный профиль:
2 CPU, около 4 ГБ RAM и 20 ГБ диска. Стандартный: 4 CPU, 8 ГБ RAM и 30 ГиБ
свободного диска. Нужен публичный домен с прямым IPv4 A-record без AAAA/CDN.

Перед применением плана оператор подтверждает установку пакетов Docker, когда
она необходима, и условия Let's Encrypt. TCP 80/443/3478/5349/50010 и UDP
3478/50010/49160–49259 должны быть доступны извне. Управление облачным firewall
не входит в протокол. Неизвестные существующие установки и занятые порты
отклоняются; интеграция с работающим сторонним reverse proxy не выполняется.

Задание продолжает работу через systemd после закрытия SSH. `cancel` ожидает
границу команды; это не принудительное завершение apt, сборки или миграции.
`resume` использует исходный план. Остановка и восстановление не удаляют Docker
volumes, не меняют сохранённые секреты и не выполняют `compose down -v`.
Локальная резервная копия перед миграциями не заменяет внешнее резервирование.
